# Locks

Written against commit `b0d98ee7`. Every `file:line` below is at that commit. Unless a path is given, lines are in `dm/gfx/nvn/nvn_mtl.m`. Short file names: `hle_nvn.c`, `nvn_rec.h`, `nvn_dirty.c`, `nvn_geometry.inc`, `nvn_capture.inc` and `host_msl.m` are in `dm/gfx/nvn`; every other file named without a folder is in `dm/host`.

Every lock of `dm/gfx/nvn` and `dm/host`: what it guards, which threads take it, the order in which locks nest, and where a lock is held across calls that take other locks.

Other files of this folder: [nvn-state.md](nvn-state.md) (the globals each NVN lock guards), [host-threads.md](host-threads.md) (`G`, the wait buckets, native waits), [overview.md](overview.md) (every thread), [nvn-pipeline.md](nvn-pipeline.md) (the submit and present paths), [lifetimes.md](lifetimes.md) (deferred release and residency).

## How this was made

1. Each translation unit of `dm/host` and `dm/gfx/nvn` was parsed with clang at BASE (`-fsyntax-only -fobjc-arc -Xclang -ast-dump`, with Pokopia's generated profile header), as for [nvn-state.md](nvn-state.md#how-the-inventory-was-made).
2. Every call of `pthread_mutex_lock` / `_trylock` / `_unlock`, `os_unfair_lock_lock` / `_unlock`, `pthread_rwlock_*`, `dm_host_mutex_lock`, `dm_host_lock`, `pthread_cond_*wait*` and every `@synchronized` was attributed to its function, with the set of locks held at each statement.
3. A nesting `A` → `B` means `B` is taken while `A` is held: in the same function ("direct"), or in a function reached from a call made while `A` is held ("through `callee`").
4. Threads: the roots of the call graph that reach the function taking the lock. `h_*` entry points are game threads (`h_nvnQueueSubmitCommands` is "submit"); the thread functions of [overview.md](overview.md#threads) are named after their thread; blocks given to GCD are "GCD"; blocks given to Metal feedback, completion and listener handlers are "Metal handler".

Limits. The held set is path-insensitive: an unlock inside a branch, a `cleanup` attribute that unlocks at the end of a scope (`PATH_LOCK`, `txn_guard`), and a lock released by a callee (`post_run`) are not always seen, so a reported nesting can name a lock that was already released. The call graph counts every call whatever its condition and misses calls through function pointers. So the Threads column, and every nesting "through" a callee, is (unverified) unless the Checked column of [Nestings](#nestings) says yes. Reports found false on reading are in [Reported nestings that are not](#reported-nestings-that-are-not).
