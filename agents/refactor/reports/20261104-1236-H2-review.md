## Checks

At every release of `G`, `wkind != 0` holds exactly when the thread is linked. No other file touches these fields: `thr_t` is private to `hle_thread.c`, `entry.S` uses no `thr_t` offsets, and `rg` finds no other user of `g_wait`.

### Same waiters found, same order: holds

- **Kinds 1-3.** A waiter with (kind k, key a) always sits in `wait_head(k, a)`, and every scan of that bucket keeps the old predicate (`wkind == k` and `waddr` / `wkey == a`). The sets that `pick`, `more`, `left` and `nw` see are the ones the full scan saw.
- **Order for kinds 1-3.** `pick` takes the minimum (`prio`, `wseq`), and `wseq` is unique (`++g_wseq` at `:261`, `:305`). The chosen waiter therefore never depended on list order, and the buckets keep Horizon's priority-then-FIFO choice. This includes a waiter that 0x1D converts to a lock wait: it gets a new `wseq` and goes after the lock's existing waiters at equal priority, as before.
- **Kind 4.** `g_wait_sync` holds exactly the kind-4 waiters. They are pushed at the head as `g_wait` was, and none ever moved in the old list. `wake_sync_waiters` therefore wakes the same set in the same relative order (newest first, as before).
- **Iteration safety.** The `n = w->next` capture in `wake_sync_waiters` stays safe: `wake` unlinks only `w`. The 0x1D loop calls `pick` afresh each time, so a converted waiter that lands back in the same bucket is filtered out by kind.

### Hash and bucket count: fine

Correctness does not depend on the hash: every scan filters on kind and key. The multiply-shift hash takes its top 8 bits, which depend on every key bit, so 4- or 8-aligned guest addresses spread well. Folding in the kind with XOR separates one address used as a lock (kind 1) and as an arbiter key (kind 3). Many waiters on one key still share one bucket, at the old per-key cost. 256 heads take 2 KiB.

### `dm_guest_clock_advanced` over `g_all`: equivalent, negligible cost

- **Same set.** In the old code, the set of threads with `wkind != 0` was exactly the `g_wait` set (see the invariant above), so `g_all` filtered by `wkind` reaches the same threads.
- **Threads not yet in `g_all`.** CreateThread links the thread into `g_all` (`:956`) before it returns the handle (`:958`). The thread cannot reach `block` before StartThread, and StartThread needs that handle. Its wait for `started` on `cv` (`:350`) has `wkind` 0 and was never signalled. The main thread is linked in `svc_thread_main_init` before any guest code runs.
- **Threads leaving `g_all`.** Only `thr_free` removes threads, and only exited ones, which have `wkind` 0.
- **Cost.** `g_all` also holds exited threads whose handles are still open, but this runs once per present and only under `DM_DETCLOCK` (`hle_os.c:70`). Other `g_all` walks under `G` already exist (`dm_yield_to_core_peers`, `dm_yield_top`).

### Would `t_waitq` catch a missed re-bucket? Yes, for the paths it drives

- **The invariant check.** `buckets_consistent` (`t_waitq.c:32`) checks four things:
  - the `pprev` chain;
  - that each linked thread sits in `wait_head(wkind, its key)`;
  - that every unlinked thread in `g_all` has null links;
  - that the number of linked threads equals the number of threads in `g_all` with `wkind != 0`.
- **Rekeying in place.** `condition_wait_becomes_lock_wait` (`t_waitq.c:111`) picks a condition key whose kind-2 bucket differs from the lock's kind-1 bucket (`:113`). Rekeying in place without a relink would fail two asserts: the bucket assert and `waits_in(&cw.t, 1, lock)`. The lock release would also never find the waiter, so `alarm(20)` would end the run. The same test checks the equal-priority order after the conversion (`lw` first, holding `WAITERS_BIT`).
- **Missing unlinks.** A missing unlink on wake or timeout fails the count or the null-link assert. `timeouts_leave_no_waiter` covers the immediate path, wall-clock timeouts of kinds 2, 3 and 4, and the converted lock wait. `guest_clock_reaches_every_waiter` covers the deterministic timeout, including a converted waiter.
- **Unlinking at every position.** `colliding_keys` and `sync_waiters_in_their_own_list` unlink from the head, the middle and the tail of a shared chain. They also cover an event signal, a cancel and a thread exit.
