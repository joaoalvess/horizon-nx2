## What was checked and holds

- **Every free of a `thr_t`.** `thr_free` has three callers: `thread_exit` (`hle_thread.c:404`), CloseHandle (`:1217`) and the new last unpin (`:1056`). Nothing else frees a `thr_t`: the other `free` calls (`:1211`) free events. Each of the three tests the other two conditions of {`closed`, `exited`, `pins == 0`}, and every change to them happens under `G`. `pins` can only go up through a successful `h_get`, which needs an open handle: `closed == 0` at lookup, and `H_CUR_THREAD` gives `t == me`, which is rejected. Once `closed` is set, `pins` can only go down. So the object is freed exactly once, at the last of the three events. All orders were checked: exit/close/unpin, close/exit/unpin, exit/unpin/close, close/unpin/exit.
- **The last-unpin free.** It runs under `G`, after the loop. Nothing reads `t` after it: `:1058-1060` use only `regs`. No thread can still be waiting on `pcv`. The target has exited, so it cannot be in `on_pause_sig` or `thr_svc_leave`, and any other pauser would still hold a pin. The `cv_pend` spin waits only for other threads' `cv_flush`.
- **Two pausers.** `pins` is a count, and the last pauser out frees the object. `two_pausers` tests exactly this.
- **Lock order and the H3 invariant.** The diff adds no lock. SetThreadActivity queues no `cv_signal`: `hand_wake` broadcasts `g_hand_cv` directly. The caller also enters `svc_thread_impl` with an empty queue. Every `wake` / `cv_signal` / `wake_sync_waiters` call is in `svc_thread_impl` (flushed by `svc_thread`), `thread_exit`, `dm_guest_clock_advanced` or the `hle_signal_*` functions, and `block` flushes under `G`. So the loop's re-locks of `G` never hold back a `cv_flush`. The new `thr_free` site waits only on flushes that take no `G`, so it cannot deadlock.
- **H5 (`hand_wake`, `g_hand_cv`).**
  - `hand_wake(t)` still runs before the pin (`:1044`), and `thread_exit` still calls it at exit (`:401`).
  - A pinned thread that has exited and been closed stays in `g_all` until the unpin. Before H9, an exited thread whose handle was still open stayed there too.
  - `dm_yield_to_core_peers` skips exited threads. `hand_wake` and `note_runnable` read that thread's fields from memory that is still allocated.
  - The late `thr_free` clears `hand[]` and `start_by`. A start wait whose starter is pinned ends at that free, or at the 5 ms bound. Before H9, a starter with its handle still open behaved the same way.
- **The test drives the race deterministically.**
  - Signal window: `slow_kill` runs the close and the exit before it reads `*pt`, while `G` is released.
  - Wait window: `slow_wait` runs them in place of the timed wait.
  - With the bug present, `race()` writes the `[RED]` freed-early line.
  - Mutants that are caught:
    - drop the guard in `thread_exit`: caught by CLOSE_EXIT;
    - drop the guard in CloseHandle: caught by EXIT_CLOSE;
    - drop the unpin free: caught by "never freed";
    - drop `exited` from the unpin condition: caught by CLOSE_PAUSE.
  - One mutant gets through (N1).
- **The docs entry matches the code.** Symptom, Cause, Fix and Check describe `:1048-1056`, `:404` and `:1217`. The symptom index is current. Both Atmosphère claims match the sources:
  - `kern_svc_activity.cpp`: `KScopedAutoObject thread = ...GetObject<KThread>`.
  - `kern_k_thread.cpp`: `KThread::SetActivity` has `R_SUCCEED_IF(this->IsTerminationRequested())` in the pause loop.

## Findings

**N1 (nit, test gap): `dm/host/tests/t_pause_exit.c:121-138`, against `hle_thread.c:1056`.**
- No case has the target exit while pinned and keep its handle open past the unpin. In CLOSE_EXIT and EXIT_CLOSE the handle is closed inside the window, in CLOSE_PAUSE the target has not exited at the unpin, and `two_pausers` closes the handle as well.
- So the mutant `if (!--t->pins && t->exited) thr_free(t);` (`closed` dropped) passes every case.
- Failure it would let through:
  1. A collector pauses a thread.
  2. The thread exits during the loop, with its handle still open.
  3. The unpin frees it.
  4. The game's later WaitSynchronization or CloseHandle on that handle reads freed memory.
- Fix: add a fourth order, "exits in the window, closed after the SVC returns", that checks the object is freed only at the CloseHandle.

**N2 (nit, test pins a non-Horizon result): `dm/host/tests/t_pause_exit.c:148-155`.**
- `two_pausers` requires the second pause of a target whose pause is already requested to return 0.
- On Horizon that call returns `svc::ResultInvalidState` (`KThread::SetActivity`: `R_UNLESS(!this->IsSuspendRequested(SuspendType_Thread), svc::ResultInvalidState())`).
- The host's success was there before H9, but the test now treats it as expected behaviour. If the result code is ever made to match Horizon, this case fails. The pin logic would still be right: a pause, a resume by a third thread, then a new pause can give two loops on one target.
- Fix: none required now. Note the divergence, or build the second loop through pause / resume / pause.

**N3 (nit, docs wording): `docs/reference/threads.md:55`.**
- "No path takes `G` between a release of `G` and its `cv_flush`" is false if read literally. The pause loop itself releases and retakes `G` (`hle_thread.c:1050`, `:1053`) before `svc_thread`'s `cv_flush`.
- It is safe only because this SVC queues no signal (see H3 above).
- Suggested wording: "SetThreadActivity queues no deferred signal, so the `thr_free` at its last unpin waits on no flush of its own, and no flush takes `G`."

**N4 (nit, existing comments now incomplete): `hle_thread.c:75`, `hle_thread.c:1206`.**
- The comment on `closed` ("freed only when this holds together with exited") is still true as a necessary condition.
- CloseHandle's "the object is freed once the thread has also exited" now leaves out "and no pause holds it".
- The rules forbid editing comments, so leave them. This is noted only.

**I1 (info, state files after the join; the main thread writes them).**
- `agents/architecture/host-threads.md:319` (the "SetThreadActivity pause loop" row of "Accesses outside `G`") becomes wrong.
- Lifecycle steps 4-5 (`:95`, `:98`: "`thr_free` if `closed`", "if already exited") should add "and not pinned".

**I2 (info, pre-existing, outside scope): `hle_thread.c:1049-1050`. The pin keeps the `thr_t` alive, not the pthread.**
- The loop tests `!exited` under `G`, then releases it. The target can run `thread_exit` to `pthread_exit` before `pthread_kill(t->pt)`, which then signals a detached thread that has terminated (POSIX UB).
- On Darwin this is benign. `pthread_kill` checks the thread list and returns `ESRCH`. If a new pthread reuses the struct, it gets a SIGUSR2 that `on_pause_sig` ignores (no `g_keythr`, or no `pause_req`).
- The docs entry claims only that the object stays alive, which is accurate.

**I3 (info, pre-existing, outside scope; candidate item): `hle_thread.c:1025-1033` (0x0E GetThreadCoreMask, 0x0F SetThreadCoreMask) and `:1071` (0x25 GetThreadId).**
- They look up and dereference a `thr_t` without `G` at all.
- A CloseHandle on another thread can free an exited target under `G` during the read. This is the same class as H9, reachable only by a game that closes a handle while another of its threads still uses it.

**I4 (info, pre-existing, outside scope, not run): `hle_thread.c:446`, `:466`. Reading the context of a thread that exited while paused.**
1. ExitThread's `thr_svc_enter` marks a thread with a pending pause as `paused` and leaves `svc_regs` pointing at the gate frame on its pthread stack. `thr_svc_leave` never runs for it.
2. GetThreadContext3 on that handle, still open after the exit, makes `ctx_fill` read the stack of a detached pthread that has terminated.
3. On Horizon a terminated thread fails the state check in `SetActivity` (`ResultInvalidState`).
