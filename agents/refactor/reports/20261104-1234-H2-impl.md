## What the diff does

1. `g_wait` is gone. Lock (1), condition (2) and address (3) waiters hang in `g_wait_key[256]`, hashed by kind and key (`wait_head`, `:219-222`: Fibonacci hash of `key ^ kind`). Each chain is doubly linked through `next` and a new `pprev` (hlist style), so `wait_unlink` takes O(1) and needs no head (`:228-231`).
2. Sync-object waiters (4) have their own list, `g_wait_sync`, which `wake_sync_waiters` walks (`:576`). `pick`, `lock_handoff`'s `more`, SignalProcessWideKey's `left` and SignalToAddress's `nw` scan only the key's chain.
3. `lock_acquire_for` unlinks the waiter, rekeys it, then relinks it in the lock's bucket (`:303-306`). `dm_guest_clock_advanced` walks `g_all` and signals every thread with a `wkind` (`:587`).

## The item's caveats, as implemented

- **Every write of `wkind` / `waddr` / `wkey` re-buckets.** Every write in the file (`rg "(wkind|waddr|wkey)\s*="`):
  - `wake` `:256` and `block` `:262`, `:273`, `:277`: `wait_unlink` first, then `wkind = 0`.
  - `block` `:261`: `wkind = kind`, then `wait_link`, which reads the key fields at that moment.
  - `lock_acquire_for` `:303-306`: unlink, write `wkind` / `waddr` / `wtag` / `wseq`, then link.
  - ArbitrateLock (`:1039`), WaitProcessWideKeyAtomic (`:1064`; also `:1069`, the `DM_TEST_CV_OLD_ORDER` variant) and WaitForAddress (`:1094`) write `waddr` / `wkey` on the calling thread (`cur()`), inside its SVC. It has `wkind == 0` and is not linked, and the `block` that follows links it with those values.
  - `calloc` in CreateThread and main init: zero, so not linked.
  - `hitch_grab` `:460` writes a `hitch_t` copy, not the `thr_t`.
- **Kind 4 has its own index:** the `g_wait_sync` list. It matches through the handle arrays, which are still read through `g_h` at signal time, exactly as before. An index by object was rejected. It would need a handle-to-object snapshot at block time, which would change behavior when a handle is closed or reused during the wait. It would also need one node per handle (up to 64) allocated under `G`. Sync waiters are few: 1 of 58 waiters in Pokopia's dump, 0-1 of 89 in MKW's.
- **`lock_acquire_for` rekeys:** it now moves the waiter between buckets, and the `wseq` renewal is kept. The comment on that line said "Still in g_wait". My change made it wrong, so I changed it to "Changed to a lock wait, in the lock's bucket". **This is the only comment change.**
- **`dm_guest_clock_advanced` reaches every waiter:** it walks `g_all` filtered by `wkind`. That is the same set as the old `g_wait`, because a thread is linked exactly when its `wkind` is not 0. It is called only under `DM_DETCLOCK`.
- **Unchanged:**
  - Wake order and kernel order: `pick` still selects by priority, then `wseq`, which is a total order. `wake_sync_waiters` wakes kind-4 waiters in the same order as before (most recent first).
  - Item H1's redundant scans are left in place (out of scope); each now walks one chain.

What the numbers mean:
- **Saving per scanning SVC:**
  - Warm, in the Pokopia mix: 40-110 ns and 300-900 instructions per SVC, all of it time under `G`.
  - Warm, in the MKW mix: 120-280 ns.
  - Cold: 4.5-9 µs.
- **Cost:** a link + unlink pair costs about 27 instructions more (the hash and the `pprev` upkeep), +0-3 ns warm.
- **The rate:**
  - I could not get the mix of SVCs, because the logs count all SVCs together.
  - If a third of Pokopia's 71 k SVC/s scan, the warm saving is about 2-4 ms/s, 0.2-0.4 % of a core.
  - With MKW's 166 k SVC/s, the warm saving is about 7-15 ms/s.
  - Lines that other cores evict make each scan cost more, up to the cold figures.
- **Overall:** the catalog's 1-2 % of a core lies within this range, and I cannot pin it down without a boot. Shorter holds of `G` also mean less contention between the game's threads, which this benchmark does not measure.
