### 1. Nit (docs): no reference entry for the general mechanisms found in this range

The fall-through after `blr x16`, and the `cbz x17, 1f` that jumps across the label through a temporary label, then land in unrelated code. B1's commit message says every big-stack call did exactly that.
- B1, `-Wl,-export_dynamic`. Under LTO, `ub_var`'s `dlsym` (`nvn_mtl.m:1432-1437`) stops finding unregistered globals unless the executable exports them.

### 5. Outside the diff, old (log only): `nvnWindowSetPresentInterval` can log the big-stack entry instead of the game's call site

- **Where:** B1 made `h_nvnWindowSetPresentInterval` `noinline` (`hle_nvn.c:1367-1369`), so `__builtin_return_address(0)` stays the function's own return address. That address is not always the game's.
- **Why:** every implemented NVN function outside `nvnCommandBuffer*` goes through `nvn_big_entry` → `dm_bigstack_enter` (`hle_nvn.c:1332-1337`, `nvn_entry.S`). On a thread whose sp is in the guest block, that path switches stacks and calls with `blr x16`. The return address is then `_dm_bigstack_ret`, `module_of` returns NULL, and the line reads `(from ?+0)`. `hle.h:50` already describes the fix: `dm_bigstack_caller`, which the audio entries use.
- **Not a regression:** this predates the range, and B1 neither causes it nor fixes it. DK's logs show `main+0x204c20` (`runs/s2_dk_play.log`), so DK calls from the guest main thread, whose stack is the pthread's own and gets no switch.
- **Failure scenario:** a game that sets the interval from a render thread logs `?+0`, and the call site cannot be found from the log.
- **Fix, if wanted:** `dm_bigstack_caller(__builtin_return_address(0))` in that one function. Other cases:
  - `nvnMemoryPoolInitialize` and `nvnProgramSetShaders` read `__builtin_frame_address(0)` for backtraces. Those walk on through `dm_bigstack_enter`'s frame record (`stp x29, x30, [sp,#0x90]` on the guest stack), so they are unaffected.
  - The `nvnCommandBuffer*` readers never take the switch.

## What holds (the interactions the brief named)

### ThinLTO with the weak / strong `dm_sdk_ounce`

- **Host:** the weak definitions at `hle_nvn.c:183-186` (`dm_sdk_major`, `dm_sdk_ounce`, `dm_sdk_nvn2_item`, `dm_glslc_gpu_code`) lose to the strong ones in `loader.c:151` and `hle_glslc.c`. All of them are LTO bitcode. A non-ODR weak definition is interposable, so it is never inlined before resolution. After resolution, the copy that does not prevail is dropped, not kept as `available_externally`.

- **`-export_dynamic`:** it keeps the prevailing copy of each global, here the strong one. With two definitions of different strength there is no duplicate-symbol error, and LTO cannot fold `g_sdk_ounce`, which is exported and written in `main`.
