# R1 review: `nvn_replay` submit and process instruction counters

Verdict: **approve with nits**

Diff reviewed: `git diff -- dm/gfx/tests/nvn_replay.m` (uncommitted on `refactor`, 5 insertions, 1 deletion). Read-only: nothing in the repository was built, run or edited. Kernel semantics were checked against the public XNU sources (`apple-oss-distributions/xnu` main: `osfmk/kern/recount.c`, `bsd/kern/sys_recount.c`, `osfmk/kern/task.c`, `osfmk/kern/bsd_kern.c`), and `sysctl kern.precise_user_kernel_time` was read on this Mac (M4, macOS 27.0.1): `1`. To check the new `#include`, system headers alone were preprocessed in the scratchpad (`clang -E -dM`).

The change is correct and in scope: no comments, no reformatting, no other file touched. It cannot change what the replay sends to Metal. The findings below are about how to read the two numbers, plus two small robustness nits.

## What holds

- **Thread counter.** `thr_instr()` (`dm/gfx/nvn/hle_nvn.c:1239`, in the same translation unit through `#include "../nvn/hle_nvn.c"`) calls `thread_selfcounts(THSC_CPI = 1)`. The kernel side (`sys_recount.c` `_selfcounts` → `recount_current_thread_usage`, `recount.c:551`) returns the calling thread's lifetime count plus the live snapshot since its last update, so the value is exact at the call. `recount_usage_instructions` (`recount.c:487`) sums every level: user, kernel (syscalls, page faults, the dirty tracker's faults) and secure. Instructions are architectural, so the count does not depend on P/E-core placement. Spin loops are the exception (finding 2).
- **Process counter.** `proc_pid_rusage(RUSAGE_INFO_V4).ri_instructions` comes from `fill_task_rusage` (`bsd_kern.c:1264`) → `task_power_info_locked` (`task.c:6857`) → `recount_task_usage_perf_only`. That is the sum of the task's per-CPU lifetime tracks over every thread, terminated ones included, at all levels. With `kern.precise_user_kernel_time = 1`, each thread's usage is absorbed into the task track at every user/kernel transition (`recount_transition`, `recount.c` ~1060) and at context switches. The calling thread is therefore exact at `ru0`/`ru1`, because the syscall entry absorbs it. Any other thread is exact up to its last transition.
- **Nesting.** `ru0` < `i0` < … < `thr_instr()` < `ru1` (`nvn_replay.m:347,351`), so the process span contains the thread span. The constant overheads (`ru0`'s kernel exit path and both `thread_selfcounts` syscalls in the process figure, the syscall tails in the thread figure) are a few thousand instructions a submit, the same in every build.
- **Span.** It covers `mtl_sub_begin` through `mtl_sub_commit`. This is the live counterpart of `g_sub_instr`, whose submit thread is also measured with `thr_instr`. Calls cannot be reordered across the counter reads: they are external calls with unknown side effects.
- **The DK encode thread does not work past `mtl_sub_commit`.** The brief's suspicion does not hold. `mtl_sub_commit` ends with `rec_commit` → `rec_signal` → `rec_drain()` (`nvn_mtl.m:1640-1642`). `rec_drain` publishes the open block and waits while `g_rb_head || g_rb_busy` (`nvn_rec.h:218-225`). Once it returns, the encode thread has run every record of the submission, including `RO_COMMIT` (with its `ubc_wait`), `RO_SIGNAL` and the object releases. No `dealloc` in `nvn_rec.h` puts records, so the `objc_autoreleasePoolPop` after the drain cannot queue new work. What escapes is only the encode thread's few instructions between `pthread_cond_broadcast(&g_rb_idle)` and its next `cond_wait`. Those are absorbed at its next syscall, often after `ru1`: well under 1k instructions.
- **The setup phase does not leak into the span.** `fill_tex` commits and waits synchronously (`q_cb()` drains, then `waitUntilCompleted`, `nvn_replay.m:163-168`). The `PDIF` copies and the `TREG`/`SREG` registrations run before `t1`.
- **Readers of the line.** The only parser is `scripts/regress.py:1271-1272` (`REPLAY_DIGEST`, `REPLAY_PIXELS`). Both are anchored at `^replay N: digest …` / `^replay N: … pixels differ`, and neither reads `submit CPU`, so the new fields cannot break them. `dm/tools/tests/test_regress.py:215-217` builds its own synthetic lines, which are not affected. The `--repeat` parent (`nvn_replay.m:205-218`) parses no child output. No doc quotes the line's format: the hits in `docs/development.md:765` and the game notes are about the live log. Nothing under `/Volumes/Hangar/Games/overnight` parses it.
- **No change to the replay.** The counter calls touch no replay state. `#include <libproc.h>` before `nvn_mtl.m` adds 1,668 macros to the translation unit. The only one that is also an identifier in `dm/gfx/nvn`, `dm/gfx/tex`, `dm/gfx/vk`, `dm/host/dm.h` or `nvn_replay.m` is `S_ISREG`, which `<sys/stat.h>` (included by `nvn_mtl.m:12`) defines identically.
- **The base replayer counts the same way.** `/Volumes/Hangar/Games/overnight/base-rp-b0d98ee7/dm/gfx/tests/nvn_replay.m` is byte-identical to the working tree's file (checked with `diff`), so base and head carry the same counter code.

## Findings

### 1. Submit-caused CPU that neither number sees (interpretation, medium)

- **Where:** the span ends at `nvn_replay.m:351`, and `mtl_finish()` follows at `:353`.
- **What falls outside:**
  - The commit's feedback handlers run on Metal's completion thread during `mtl_finish`: `gpu_tag_done`, `ws_fb`, `post_complete` → `post_run` (the CPU-side writes: event values and counter reports into guest memory), `defer_drain` and `gp_report` (`nvn_mtl.m:1627-1634`, `1616`, `1645`).
  - Background work that the span starts and that finishes after it: `pso_build`, `shader_load` and pull prefetches on `pp_bg_queue()`/utility queues (`nvn_mtl.m:6862`, `6943`, `7184`, `10817`). Replays 1-4 do this; warm replays should not, but nothing in the output shows that a measured replay kicked none.
- **A split that depends on timing:** `post_complete` broadcasts `g_done` (`nvn_mtl.m:1600`) before the handler's `defer_drain()` (`:1633`), so `mtl_finish` can return while the completion thread is still releasing. The next `mtl_sub_begin` also calls `defer_drain()` (`:814`), on the submit thread, inside the next span. Whichever thread takes `g_deferred_mu` first does the releases, so release work moves between "outside both numbers" and "inside `submit instructions`" from run to run. This is one plausible source of the 4-22 % spread between warm replays.
- **Failure scenario:** a refactor item moves work from the submit path into a feedback handler, `defer_drain` or a background queue, for example a lifetime or deferred-release change. Both numbers then drop, and the item reads as a CPU win when the work only moved off the measured span.
- **Suggestion:** state this limitation in `commands.md` (Replay CPU). For items that touch completion handlers or deferred release, also take a process delta over `mtl_sub_begin` … `mtl_finish()` (the waits block in `pthread_cond_timedwait`, so they add few instructions). That needs a second span in the replayer, a separate change.

### 2. Busy-wait instructions are counted as work (interpretation, low-medium)

- **The spin:** `ubc_wait` (`nvn_rec.h:40-48`) spins on `g_ubc_done` with `__builtin_arm_yield()` and never sleeps, so the instructions it retires grow with the wait.
- **Where it runs inside the span:**
  - On the submit thread, for games without the encode thread (Pokopia): at every main commit (`rec_commit`, `nvn_rec.h:332`) and on CPU reads of shadows (`nvn_mtl.m:1266`, `1320`, `7904`).
  - On the encode thread, for DK: `RO_COMMIT`, `nvn_rec.h:117`, counted in `process instructions`.
  - The copy worker's own 2,000-iteration spin after each burst (`nvn_rec.h:31`) adds to `process instructions` once per burst.
- **Failure scenario:** a build makes the submit thread faster but not the uniform copy worker. The submit thread reaches the commit earlier and spins longer, so `submit instructions` falls by less than the work did, or rises. Scheduling of the copy worker (QoS, core placement) also shows up as spread.
- **Suggestion:** when a change is near the threshold, repeat the comparison with `DM_NVN_UB_COPY_THREAD=0`, where the copies run on the submit thread and nothing spins (it measures a different path, so only as a control).

### 3. Nit: `submit CPU` now includes the counter syscalls

- **Where:** `t1` is taken at `nvn_replay.m:343`, and `exec_ns` is stamped at `:352`, after both `proc_pid_rusage` calls and both `thread_selfcounts` calls.
- **Effect:** each submit's `submit CPU` gains their cost, a few µs each; `proc_pid_rusage` takes the task lock and the power-info path. `submit CPU` from this replayer is therefore not comparable at the µs level with replayer output from before R1. Base against head is unaffected (see "The base replayer counts the same way" above).
- **Span widths:** the `exec_ns` span is also slightly wider than the counters'. It includes `mtl_stats` (`cp_report`) on the first submit, `mtl_set_frame` and `mtl_set_queue_origin_lower_left`, so "the same span" holds only approximately.
- **Fix, if wanted:** take `now_ns()` right after `mtl_sub_commit()` and stamp `exec_ns` from that.

### 4. Nit: `proc_pid_rusage`'s result is not checked

- **Where:** `nvn_replay.m:347,351`. `ru0`/`ru1` are uninitialised stack structs.
- **Failure scenario:** if the call fails (a sandbox profile that denies `proc_info` on self, or a flavour the kernel refuses), `process instructions` prints the difference of two stack garbage values without any warning. `thr_instr` zero-initialises its buffer and degrades to 0 instead.
- **Fix:** zero-initialise both structs, or print `?`/`[RED]` when the call returns non-zero. Unlikely to fire on the Mac command line.

### 5. Note: `process instructions` is exact only with precise user/kernel time

- **Condition:** with `kern.precise_user_kernel_time = 0`, the task track is updated only at context switches (`recount_switch_thread`). At `ru1` the calling thread's own work since its last switch is then missing, and it moves into a later span.
- **Where that applies:** it is 1 on this Air (M4). A replay run on another machine, such as the Pro server's M1, should check the sysctl first.
- **The thread counter is not affected:** `submit instructions` stays exact, because it adds the live snapshot.
