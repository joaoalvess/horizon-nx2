Verdict: **approve with nits**

The shared tree's `dm/host/hle_thread.c` and `dm/host/tests/Makefile` equal HEAD plus the patch (`git diff HEAD` compared hunk by hunk with the patch), and `dm/host/tests/t_cvsignal.c` equals the patch's new file. ## What the diff does

- `thr_t` gains `_Atomic int cv_pend` (`:58`): signals queued for this thread and not yet issued.
- A per-host-thread queue: `static __thread thr_t *g_cv_defer[16]`, `g_cv_ndefer` (`:256-258`).
- `cv_signal(t)` (`:259-263`): when the queue is full it signals at once (under `G`, every caller holds it); otherwise `cv_pend++` (relaxed) and queues `t`.
- `cv_flush()` (`:264-267`): for each queued `t`, `pthread_cond_signal(&t->cv)` and then `cv_pend--` (release); empties the queue.
- `wake` (`:269`), StartThread (`:982`) and `dm_guest_clock_advanced` (`:603`) call `cv_signal` instead of `pthread_cond_signal`.
- `cv_flush` runs:
  - in `block` before its first wait (`:282`, with `G` held);
  - after `svc_thread_impl` returns (`:944`);
  - after the unlock in `thread_exit` (`:389`), `dm_guest_clock_advanced` (`:605`), `hle_signal_system_event_binding` (`:1250`), `hle_signal_system_event` (`:1263`) and `hle_signal_bound_system_event` (`:1282`).
- `thr_free` waits with `sched_yield`, holding `G`, until `cv_pend` is 0, then destroys `cv` / `pcv` and frees (`:376-377`).
- New test `t_cvsignal`, in `run` (`dm/host/tests/Makefile`, `-DDM_TEST_THREAD_ENTER`).

No comments were added, nothing was reformatted, and `git diff --check` is clean.

### 2. Signals to a thread whose `thr_t` `thr_free` has destroyed: holds

- Both `thr_free` callers hold `G`: `thread_exit` (`:387`) and CloseHandle (`:1197`).
- `cv_pend++` happens under `G`, so `thr_free`'s load (`:376`) under the same mutex sees it.
- `cv_flush` touches `t` last in its release decrement, after `pthread_cond_signal` has returned (`:265`). The acquire load at `:376` pairs with that decrement, so `pthread_cond_destroy` and `free` come after the signaller's last access.
- A signal sent at once when the queue is full (`:260`) is sent under `G`, so it cannot overlap `thr_free`.
- `t` can appear twice in a queue (StartThread on itself, for example); the count handles that.

A self-deadlock would need a thread to call `thr_free(x)` with `x` in its own queue. That cannot happen:
- `thread_exit` frees itself, and its queue holds only kind-4 waiters, which are linked and therefore not exited.
- CloseHandle queues nothing, and starts with an empty queue.

The spin in `thr_free` would deadlock if a thread with a non-empty queue had to take `G` again before flushing. By the table above, no path does: each flush comes right after the unlock, or under the same hold (`block`).

### 3. Which guest thread wakes, result codes, lock words, wake order: holds

- `wait_unlink`, `wkind`, `woke`, `wres` (`:269`), the lock word (`:307`, `:314`), the address word (`:1131`), the condition key (`:1099`) and `note_runnable` are all written under `G` before the signal, as before.
- Every waiter re-checks `woke` (or `started`) under `G` (`:283`, `:291`, `:364`). So a later signal is never lost:
  - when the waiter is already in `pthread_cond_wait`, it is blocked on `cv` when the signal comes;
  - when it is not, it sees `woke` before it waits.
- A late signal that reaches a newer wait of the same thread is a spurious wake, which the `while (!t->woke)` loop absorbs, as it already did for `dm_guest_clock_advanced`'s signals.
- The order in which threads are picked (`pick`, kernel order) is unchanged.
- Handoffs still work: `svc_thread` flushes (`:944`) before `dm_yield_to_core_peers` (`:950`), so a woken higher-priority same-core thread has been signalled before the waker waits for it to block. The same holds before `hand_epoch++` (`:953`), which `dm_thread_service_request` polls.

### 4. Per host thread, race-free: holds

- The queue is `__thread` (`:257-258`).
- No signal handler touches it: `on_pause_sig` calls no `cv_signal` or `cv_flush`.
- Only `cv_pend` is shared, and it is atomic.

## Findings

No defects. Nits and observations:

1. **The 0x1C path still signals under `G`** (`:282`). When WaitProcessWideKeyAtomic hands the lock to a waiter, `block` must flush before it waits, and it holds `G` then, so the condition-variable wait of the SDK keeps the old cost. This is correct and unavoidable without a larger change. The item's gain reaches 0x09, 0x1B, 0x1D, 0x35, 0x11, 0x19, the thread exit, the clock step and the service events.
2. **Past 16 queued signals, the rest go out first** (`:260`): they are signalled under `G`, before the first 16 queued ones. The order of host signals is not guest-visible, and it gave no guarantee before (every woken thread then took `G` in the mutex's order), so this is an observation only.
3. **`thr_free` spins holding `G`** (`:376`). It waits only when a signal to the freed thread is still queued at that moment, and then only for the few instructions the signaller has left. If the signaller is descheduled in that window, every guest thread waits on `G` meanwhile. This is rare: it needs a wake, StartThread or clock step to the thread just before its exit and close.
4. **One invariant holds only by construction:** between releasing `G` and `cv_flush`, no path takes `G` again. A later change that adds a `G` section in such a window (for example in `svc_thread` between `:943` and `:944`, or in front of the `hle_signal_*` flushes) would make `thr_free`'s spin a deadlock. No comment can say so (rules), so the architecture docs should (below).
5. `t_cvsignal` does not cover `thread_exit`'s flush. `t_waitq` does, and it is in `run`, so this is not a gap in the suite.
