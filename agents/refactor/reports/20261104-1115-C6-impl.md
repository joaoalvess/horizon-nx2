## What the diff does

1. Five strong ObjC locals on the per-draw / per-dispatch path become `__unsafe_unretained`. ARC no longer retains the shader or program when the local is loaded, or releases it on each exit.
2. The spelling matches the unretained locals of the same kind the file already has: `:5568`, `:5573`, `:5602`, `:5606`, `:8791`, `:10336`, `:10388`, and `draw_`'s own `pr` at `:10458`.
3. Nothing else changes: the loads and the control flow are the same.

## Why each owner outlives its local

Two facts carry all five sites.

**A. A program owns its shaders for its whole life, because a published program's shader slots are never reassigned.**
- `rg -- '->sh\[[^]]*\] ?= '` over `dm/gfx/nvn` (including the `.inc` and `.h` files) and `nvn_replay.m` finds writes only to programs that nothing else can see yet:
  - in `prog_get` (`:4780`, `:4792`);
  - in `prog_fold_gs` (`:4734`). It is called from `prog_get` before `serial_put`, and from the composite path on its own new `o` (`:5650`);
  - in the composite program at `:5649`, a fresh `[NvProg new]`;
  - in the geometry raster programs (`nvn_geometry.inc:458`, `:729`). Each is a fresh `[NvProg new]`. A mismatch makes a new raster; an old one is never rewritten.
- `NvProg`'s `sh[6]` ivar is strong under ARC (`:4392`).
- Shaders also have owners of their own:
  - every non-builtin shader stays in `g_shcache` for good. Nothing in `nvn_mtl.m` removes an entry; only tests set `g_shcache = nil`;
  - builtins stay in `g_builtin` for good (`:4747-4759`).

**B. A program that the submit thread got from `prog_get` cannot be freed before the submission it is drawing in completes.**
- Its owners are the serial table `g_by_serial` (strong, through `hm_put_id`) and `prog_get`'s strong static `lpr`.
- Every removal from the table first queues the object with `defer_obj_release`, and only then drops the table's reference:
  - `serial_del` (`:1832`), which `mtl_prog_release` calls on the guest thread, from `nvnProgramFinalize` and from program re-initialisation (`hle_nvn.c:634`, `:696`);
  - `prog_serial_del` (`:1834`), the composite cache;
  - the replacement in `serial_put` (`:1831`).
- `defer_obj_release` stamps the object with `g_fence + 1` (`:289`).
  - `g_fence` advances only in `mtl_sub_commit` (`:1610`). Its only caller is the submit entry (`hle_nvn.c:1292`). It is never reached from `draw_`, `geo_draw`, `dispatch` or anything they call.
  - `defer_drain` (`:300`) runs from `mtl_sub_begin` and from the commit's feedback handler. It frees only fences `<= g_done <= g_fence`.
  - So an object queued while a draw runs lives until after this submission commits and completes.
- `lpr` is never the last owner of a program in use:
  - `lpr` is set only on a `serial_get` hit;
  - removing a program from the table bumps `g_ser_gen`, so the next `prog_get` misses the cache instead of returning the removed program.
- The existing code already relies on the same guarantee. `draw_` holds `__unsafe_unretained NvProg *pr = g_geo_program ? g_geo_program : prog_get(S.prog)` (`:10458`) across the whole draw, and `prog_get` itself returns `__unsafe_unretained`.

## Cost

Measured only through codegen.
- A draw saves about 3-4 retain / release pairs. Each pair is roughly 25-30 instructions and a few ns of atomics.
- In instructions that is about 0.1 k a draw: 0.07 M on `dk_cliff` (732 draws), 0.27 M on `pk_world` (2,730 draws). That is 0.1-1 % of submit instructions, below the replay's spread.
- In time, at 15-30 ns a draw, it is 10-80 µs a frame: the low end of the catalog's 0.05-0.15 ms.
