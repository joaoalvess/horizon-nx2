Branch `refactor`, not committed. When work started HEAD was `7421ef5f`, with C7 uncommitted in the tree. The final candidate is built from the tree at HEAD `25446564` (C7 committed as `59d2272e`, R3 as `25446564`) plus this diff. A first round of checks ran on `59d2272e` + P2 (see Round 1).

```diff
-    typeof(S) s0 = S; typeof(R) r0 = R; int pd = g_pso_dirty, dd = g_dss_dirty;
+    typeof(S) s0; typeof(R) r0; int pd = g_pso_dirty, dd = g_dss_dirty;

-    if (n > 1) memcpy(cur.ret, g_ret, sizeof(*g_ret) * (size_t)g_ret_n);
```

## What the diff does

1. `geo_draw_` now copies `S` (26,224 B) and `R` (552 B) only when the run has more than one draw (`n > 1`), which is the only case its restore at `:830` runs.
2. The copy stays at the same program point, and `cur`'s initializer reads only `g_exec_next` and `g_ret_n`. So for `n > 1` the saved state is byte for byte what it was before.
3. For `n == 1`, two `memcpy` calls (26,776 B, about 5,100 instructions) are skipped on every geometry draw that reaches the compute path. Nothing else changes.

## The claim, and what the copies protect

- **The claim holds.** At HEAD, `:815` copies unconditionally and `:830` restores under `if (n > 1)`. In the DK `cand-C7` host, `geo_draw_` calls `memcpy(sp+0x170, _S, 0x6670)` and `memcpy(sp+0x67e0, _R, 0x228)` right after `endEncoding` with no test of `n`. In the `cand-P2` host both calls are behind `cbz w20` (the `n > 1` flag, which is saved to `[sp,#0x2c]` for the restore).
- **What the restore protects (`n > 1`).**
  - The loop at `:820-829` replays the state ops between the run's draws through `state_op`. That writes `S`, `R.sc` / `R.has_sc` (`OP_SCISSOR`, `nvn_mtl.m:8434`), `g_pso_dirty` and `g_dss_dirty`, so each member's geometry dispatch sees its own state.
  - `:830` then puts back the state as it was at the run's first draw, for `geo_raster(j0)` and for `mtl_exec`. `mtl_exec` applies those ops again in order, and rasters each later member at its own op (the loop at `:789-791`).
  - `t_geometry` mode 16 is this case: two draws with an `OP_BIND_SSBO` between them, then a cover draw. It checks `g_geo_nrun == 2`, that each draw writes its own SSBO, and the pass counts.
- **Every reader of the copies.**
  - `s0`, `r0`, `pd` and `dd` are locals, and their address is never taken. Their only reader is `:830`, under `if (n > 1)`.
  - `cur.ret` is read only by `fz_next` for `i >= 1`, that is when `n > 1`.
  - `n` is assigned once at `:812`. It is not written afterwards and its address is not taken. `geo_run_walk` returns at least 1, so `n <= 1` means `n == 1`.
  - There is no `return` or `goto` between `:815` and `:830`.
  - The nested `geo_draw` calls (`geo_prep` → `geo_split`) happen at `:801`, before the copy, and each has its own frame.
- **With `n == 1` the copy was dead.** The loop runs only `i = 0` and calls no `state_op`, and the restore never ran with `n == 1`, before or after the change. Whatever `geo_gs_one(j0)` changes stays in place either way.
- **`:761` (`geo_run_walk`) is not changed: its copy is needed.** Its restore at `:784` is unconditional, and its loop can run `state_op` (through `geo_run_passes`) before any `break`.
  - Observation, not changed: when `n > 1`, `geo_draw_`'s copy at `:815` equals the walk's `s0`, which `:784` just restored. `enc_r_end` and `:813` write neither `S` nor `R`. So one of the two 26.8 KB copies per hoisted run could be shared. That is a larger change than this item.
- **Codegen.**
  - Normalized function by function (addresses and literal offsets stripped), `geo_draw_` is the only function whose code differs between `head-25446564` and `cand-P2`. This holds for the host and the replayer of both games, and also for `cand-C7` against the round-1 binaries.
  - The host `__text` size is unchanged. The replayer's `geo_draw_` is one instruction shorter.

## Cost

- **Per skipped copy:** `scratchpad/p2/micro/copy.c` (clang -O2, `noinline`, `ri_instructions` and thread CPU time over 10^6 calls, hot cache) gives:
  - 5,112-5,122 instructions and 390-518 ns for copying `S` + `R`;
  - 49 instructions and 3.4 ns when the copy is skipped.
- **Where it applies on the fork's games:**
  - *DK.* DK's only vertex / geometry pair has a mesh library (`geo_mesh.tsv`). Mesh draws return at `:793`, before the copy, so in steady state DK never reaches it. The copy runs only on compute-path geometry draws:
    - while the mesh pipeline builds (the first replay of `dk_ypunch` logs `geometry compute:` before `geometry mesh pipeline … 29.8 ms in the background`);
    - draws the mesh path does not take (indirect, instanced, restart-indexed, transform feedback, rasterizer discard);
    - with `DM_NVN_GEO_MESH=0`.
  - *Pokopia.* None of its 7 captures has a geometry draw: no `geometry` phase in `DM_NVN_CPUPROF` and no `geometry` log line.
  - *MKW.* Not measured: it cannot be captured.
  - *The catalog's 5-10 µs per geometry run (DK) does not hold.* The real figure is about 0.4-0.5 µs per run whose head does not hoist, and almost none of DK's steady-state frames have such runs.
- **Forced compute path:** `dk_ypunch` with `DM_NVN_GEO_MESH=0 DM_NVN_GEO_HOIST=0` (every geometry draw takes `n == 1`, about 95-127 `geo_draw` calls a replay: 380 in a 5.5 s profiling window). The candidate's submit median is lower than the baseline's in all 4 of 4 alternating pairs:
  - candidate 29.89-29.99 M;
  - baseline 30.34-32.16 M (median 30.46).

  The difference, about 0.5 M (1.7 %), is about what 95-100 skipped copies come to. It is within one run's spread (6-8 %), so it is not a resolved result.
