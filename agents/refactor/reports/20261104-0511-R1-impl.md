The diff is uncommitted on `refactor`. B1 was committed meanwhile (`0eec4184`; `4d0470fb` touches no `dm/` file), so the working tree is HEAD plus this diff. The candidate replayers were built from the tree while B1 was still uncommitted. That tree's `dm/` matched `0eec4184` file for file (same per-file line counts), so `cand-R1` is B1 + R1. ## What the diff does

1. Just before `mtl_sub_begin` it reads `proc_pid_rusage(getpid(), RUSAGE_INFO_V4, …)` and then `thr_instr()`. `thr_instr` is `hle_nvn.c`'s own `thread_selfcounts(1, …)` reader, already in this translation unit. Just after `mtl_sub_commit` it reads them in the opposite order, so the thread count does not include the two syscalls.
2. Over every submit of one replay it adds up the thread's retired instructions (`exec_in`) and the process-wide `ri_instructions` delta (`proc_in`). The span is the one `exec_ns` measures, minus `exec_ns`'s three setter calls (`mtl_stats` / `mtl_set_frame` / `mtl_set_queue_origin_lower_left`).
3. The per-replay line now reads `… submit CPU X ms (+ Y ms applying the captured state), submit instructions N, process instructions M, GPU …`. `regress.py`'s `REPLAY_DIGEST` regex only anchors on the line's start, so it still matches.

## Did not hold

1. **Replays 3-9 are not all warm.** In 3 of the 4 Pokopia runs, replay 3 still costs 50-77 M instructions, and in base `pk_title` replay 4 still costs 11 M, against about 5.5 M once warm. On DK, replays 3-4 carry extra process-wide work. The prewarm-done line lands after replay 1 or 2, so this is something else that warms up later; not investigated. As a result, the spread over replays 3-9 is 777-1036 % on 3 of the 4 Pokopia runs, and the median moves with how many replays are still warming up. Replays 5-9 are steady in every run here. A better statistic is the median of replays 5-9, or `--warm 15` and its last 10 replays. The night file's rule is the main thread's call.
2. **The count is not bit-deterministic.** Warm replays (5-9) of the same binary still vary by 3.8-22.5 % on the submit thread (base `pk_title`: 5.60-7.05 M). That is far tighter than wall time, but a single `--warm 9` run cannot resolve an effect under about 10 % on Pokopia, or about 5 % on DK. Cause not investigated. Candidates, all unproven:
   - `thread_selfcounts` may count kernel-mode instructions as well, such as dirty-tracker write faults on pool pages (`crash_install`) and Metal driver traps;
   - waits inside the span that spin.
3. **The process counter has blind spots.**
   - It includes every other thread of the process: the background pipeline prewarm and compiles inflate replays 1-4.
   - With the encode thread on, `rec_commit` (`nvn_rec.h` 330-331) only queues `RO_COMMIT`. Encode-thread work still running when `mtl_sub_commit` returns, until `mtl_finish`, falls outside the span, as the spec defines it. How much was not measured.
   - I believe `ri_instructions` folds in other threads' counts only at their context switches. That is unverified, and it would add a little jitter.
4. **The exit codes printed by my script are wrong** (see Checks). The replay results above come from the `MATCH` / `MISMATCH` lines and the digests.
