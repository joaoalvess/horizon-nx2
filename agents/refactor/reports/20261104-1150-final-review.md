## What holds (the interactions the brief named)

### C1's unretained `ab_buf` with C6's unretained locals and the deferred-release / fence rules

**Who owns the buffer:** the arena lists always own it. A live arena is in `g_sub_arenas` until `arena_commit` (`:5374`), then in `g_arenas`. A strong `ab_buf` never protected the block's *content*: arena reuse is fence-based (`arena_new` `:5355-5357`), not reference-based.

**Why reuse is safe:** a block is bound again only when `ab_pass == g_pass.serial` (`:7946`).
- The serial increments at every pass begin (`:4211`).
- `mtl_sub_commit` flushes the pass (`rp_flush`, `:1605`) before `arena_commit` (`:1635`).

So a reused block always lies in an arena of the current submission, which cannot be reclaimed or trimmed. Trimming needs 600 idle submissions (`:5372`).

**What C1 changed:** only when the MTLBuffer object dies.
- **Before:** a shader's strong `ab_buf` kept a trimmed arena's buffer allocated, out of the residency set (`res_remove` `:5372`), until that shader encoded again.
- **Now:** the buffer is freed at the trim.

This is reachable only when `arena_new` hands a reclaimed large arena to an ordinary request, because no smaller arena is free (`:5356`). It lowers memory sooner for games that make large geometry arenas, OCTOPATH TRAVELER II among upstream's games (comment `:5363-5365`). It opens no GPU hazard, since a non-resident buffer could not be read before either. This is not verified on that game.

**Production use of `ab_buf`:** only the non-nil test at `:7946`; the test file messages it within its own submission. `g_c0_dim_buf` was already `__unsafe_unretained` (`:7919`). It is set and read in the same dispatch (`:8171`, `:10893-10897`), from the same buffer object as before.

**No arena switch mid-block:** between each `arena_alloc(…, NULL)` and the last read of `g_cur_arena` for that block (`:8142-8144`, `:8151-8193`, `:8202-8204`, `:8210-8213`), nothing allocates. So `g_cur_arena->cpu`, `->gpu` and `->buf` always name the allocating arena, which is the old `db`.
- `USE` evaluates its buffer only under `g_res_check_on` (`:7953`).
- `cpu` is set once per arena (`:5360`), and reuse keeps the same `buf` (`:5357`).

**C6's locals:** every `NvShader` comes from one of these, and the `sh[]` writes happen only on objects being built:
- `shader_get` / `shader_get_layer` / the warm claim, into `g_shcache` (`:4706-4722`, `:8544`, `:10784-10795`);
- `g_builtin` (`:4752-4759`);
- the geometry kernels and readers, through `shader_get` (`nvn_geometry.inc:582-583`).

Those `sh[]` writes are at `:4734`, `:4780`, `:4792`, `:5649`, and `nvn_geometry.inc:458`, `:729`.

`g_shcache` is cleared only by `t_pso_warm.m:178`, `:182`, and the programs' strong `sh[]` still hold their shaders there. The program itself is held by the caller (`objc_externally_retained`) or by `prog_get`'s autoreleased return (`dispatch`, `:10851`, `:10887`).

So the unretained `sh` / `fs` / `cs` stay valid across `fb_pass_sync`, `rp_end` and the nested `fz_end` → `draw_` path. When C6's `cs` reaches `encode_args_` (`dispatch`), the write `cs->ab_buf = …` lands in a live object.
