## What the change does

`cap_pf_block` (`dm/gfx/nvn/nvn_capture.inc:220-230`) keeps its plain, depth-plane and BC paths and adds a loop at lines 227-228. For a Metal format that is none of those, the loop looks for an NVN format with `fmt_compressed(nf)` (`nvn_mtl.m:1714`) whose `nvn_fmt_to_mtl` gives that Metal format. It returns that format's `nvn_fmt_bpb` and block size (`nvn_tex.c:12-14, 32`). The test adds an ASTC 8x8 sRGB copy destination to `t_capture_live.m`, a pin of `cap_pf_block` against `nvn_fmt_bpb` for every mapped NVN format, and a `g_cap_tex_skip` check. The doc line `docs/development.md:515` no longer says that formats that are not plain texels go uncaptured.

## Checks

1. **Block, row stride, image stride and byte count for every ASTC size: correct.**
   - `nvn_fmt_to_mtl` (`nvn_fmt_mtl.c:77-78`) maps NVN 0x79-0x86 to 204 + `astc_off[k]` (LDR) and 0x87-0x94 to 186 + `astc_off[k]` (sRGB).
   - `fmt_of` (`nvn_tex.c:13-14`) takes its block from the same `k`, in the same NVN order (`nvn.h:518-545`).
   - Against the SDK enum (`MTLPixelFormat.h:262-290`), each of the 28 LDR and sRGB values gets 16 bytes and its own Metal block size: 4x4 186/204 ... 6x6 190/208, 8x5 192/210 ... 12x12 200/218. LDR and sRGB are not swapped, and the hole at 191/209 is skipped correctly.
   - HDR (222-236) still returns 0. No NVN format maps there.
   - Strides: `cap_tex_readback` (`nvn_capture.inc:239-240`) computes `row = ceil(w/bw)*16`, `img = row*ceil(h/bh)` and `bytes = img*d` from the full level size.
     - I compared this with Metal's per-block formula for all 28 formats, at 16x16 (3 levels), 100x50 (7), 13x7 (4), 17x33 (6), 1x1, 512x512 (10) and 1920x1080 (11). Every level matched, and every `row`, `img` and offset is a multiple of 16.
     - Levels and sizes that are not a multiple of the block (13x7 under 12x12, a 1x1 level under 8x8) round up to whole blocks.
     - `sourceSize` stays the level's full size. That is the texture's edge, which is the clamped size Metal requires for compressed copies.
   - `fill_tex` (`dm/gfx/tests/nvn_replay.m:150-169`) uploads with the stored `s->row`, `s->img` and `(s->w, s->h, s->d)`, so it uses exactly the readback's layout and computes no block of its own. It also checks that the replay layer's `pixelFormat` and level and slice counts equal the captured ones. Both sides make the texture with `tex_desc`, whose format comes straight from `nvn_fmt_to_mtl` (`nvn_mtl.m:1973, 1977`).
2. **The reverse mapping is unique where it matters: yes.**
   - Each ASTC LDR or sRGB Metal value comes from exactly one NVN format. Each group has its own base, and `astc_off` is injective.
   - The only Metal compressed formats that several NVN formats map to are BC1 (0x41/0x42) and BC1_sRGB (0x45/0x46). Each pair has the same 8-byte 4x4 block, and BC returns at lines 224-226, before the loop.
   - `fmt_compressed` keeps uncompressed NVN formats out of the loop. No uncompressed NVN format maps to a compressed Metal format anyway.
   - If a later table change made two compressed NVN formats map to one Metal format with different blocks, the loop would return the first. The new pin compares every mapped NVN format with its own `nvn_fmt_bpb`, so it would fail on the second.
3. **No plain or BC result changes.**
   - Plain formats and plane 1 still return at line 222.
   - BC still returns at lines 224-226 with `*bw = *bh = 4` from line 223.
   - The loop runs only where the function returned 0 before. It writes `*bw` and `*bh` only on a match, and line 229 still sets them to 1 on the 0 path.
   - `cap_digest` (`nvn_capture.inc:458`) uses `cap_pf_bpp`, which is unchanged. No other caller of `cap_pf_block` exists: I searched `dm/` for it, and `nvn_replay.m` does not call it.
4. **The tests would fail without the fix: yes, two ways that do not depend on content, plus a third that almost certainly fails.**
   - The pin at `t_capture_live.m:91-96` fails for exactly the 28 ASTC formats with the old `cap_pf_block`. I reproduced this by porting `nvn_fmt_mtl.c`'s `T[]`, `fmt_of` and `cap_pf_bpp` to Python: 28 failures before the change, 0 after, over the 135 mapped NVN formats. The depth exemption is needed only for 0x36, where NVN stores 8 bytes per texel and Metal's plane 0 has 4.
   - The new `if (g_cap_tex_skip)` check (`t_capture_live.m:97`) fails without the fix. `at` is a texture object that `OP_COPY_T2B` names (`cap_tex_obj` -> `cap_tex_read(&t, 1)`, `nvn_capture.inc:136`), and format 194 would take the skip at line 278.
   - The replay half: the frame-2 T2B of `at` and the B2T into `rt` are in one submission. `blit()` (`nvn_mtl.m:1099-1103`) puts a barrier between them. So the presented digest depends on `at`'s level-0 bytes at the start of the frame (0x81+3i), which only the TPIX carries. A replay without it would almost certainly report MISMATCH.
   - With the fix, the frame-2 regions do not overlap: 0x34000 and 0x38000 (64 bytes each) in the 256 KB pool, and `rt` at (48,48)-(51,51) against the other blocks at (8,8), (32,8) and (8,40). Level 2 of `at` (4x4 under an 8x8 block) exercises the edge-clamped blit both ways on the GPU.
5. **Callers or paths missed: none found.**
   - `nvn_capture.inc` is included only by `nvn_mtl.m:13109`, after `fmt_compressed` (1714) and the `nvn_fmt_mtl.h` and `nvn_tex.h` declarations, so the helpers are visible.
   - `NvPkg` (packaged) ASTC textures still return before the readback (`nvn_capture.inc:271`) and are replayed from the pools as before.
   - Multisampled textures are still skipped. The edited doc line now names them as the only case, which matches the code: every texture's Metal format comes from `nvn_fmt_to_mtl`, and the pin now requires all of them to be readable.
   - No docs or reference entry outside `agents/` is made wrong (I searched for "content not captured", "cannot read back" and "plain texels").
6. **Scope and leftovers.** The diff touches only the three named files. It has no debug code and adds no new comment. One existing comment is reworded (nit 1).

## Nits

You could also leave the original comment: it was incomplete after the change, not false. Either way, this does not block.
2. `dm/gfx/tests/t_capture_live.m:48-50`: the GPU round trip covers one ASTC format, 8x8 sRGB with a block-aligned level 0. LDR, non-square blocks and a level 0 that is not block-aligned are covered only by the arithmetic, through the pin and the shared formula. That is enough here, because the readback and the upload are format-agnostic once `cap_pf_block` is right. I mention it only as the limit of what the test proves on the GPU.
