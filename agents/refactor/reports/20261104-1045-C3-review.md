# C3 review: `fb_prepare` reads the sampled texture's serial without `g_rmu`

Verdict: **approve**

Reviewed: `/Volumes/Hangar/Games/overnight/patches/C3.patch` applied to `git show b2cb3e7d:dm/gfx/nvn/nvn_mtl.m` (at review time the working tree was identical to that). The line numbers below are in `dm/gfx/nvn/nvn_mtl.m` at HEAD plus the patch. They match `b0d98ee7`, the commit `locks.md` was written against, for every line cited here.

The change, `:9854`:

```c
-        os_unfair_lock_lock(&g_rmu); uint64_t ser = tid < g_ntreg && g_treg[tid].ok ? g_treg[tid].t.serial : 0; os_unfair_lock_unlock(&g_rmu);
+        uint64_t ser = h_ser((uint64_t)tid);
```

## Memory safety

- **Allocation and growth.** `g_tser` is `static _Atomic uint64_t g_tser[1 << 20]` (`:4812`), a fixed array in BSS. Nothing reallocates it, frees it, moves it or `memset`s it: the only uses in the file are its declaration, the store in `mtl_reg_tex` (`:5023`) and the load in `h_ser` (`:8826`). The only array that grows under `g_rmu` is `g_treg` (`realloc` at `:5006`), and the new read does not touch `g_treg` or `g_ntreg`. The use-after-free in the open `fz_p2_draw` / `g_treg` note in `locks.md` cannot happen on this path. The patch actually removes a `g_treg` read from `fb_prepare`.
- **Bound.** At `:9853`, `tid = (int)(tex_slot_h(...) & 0xfffff)`, so 0 <= tid < 2^20, and `tid == 0` is skipped there. `h_ser` masks with `0xfffff` again (a no-op here) and returns 0 for ID 0. `g_tser[tid]` is always in bounds. Every texture ID a handle can name has an entry, so no `< g_ntreg` check is needed.
- **Atomicity and ordering.** The writer does `atomic_store_explicit(..., memory_order_release)` inside `g_rmu` (`:5023`). The reader does an `atomic_load_explicit(..., memory_order_relaxed)` on a naturally aligned 64-bit `_Atomic`, which is single-copy atomic on arm64, so the value cannot tear. `fb_prepare` only compares the value with `R.rt.depth->serial` and `R.rt.color[k]->serial`, and uses it as the `fb_snap` key. Nothing is dereferenced through it, so relaxed ordering is enough. By write-read coherence, a registration that happens-before the draw is always seen: for example, one made before `nvnQueueSubmitCommands`, which reaches the replay through program order or `g_sub_mu`. The writer's release ordering is not needed by this reader, but it does no harm. The same pattern already serves the nine other `h_ser` callers (`:8880`, `:8899`, `:8919-8920`, `:9005-9007`, `:9111`, `:9290`, `:9458`, `:9593`, `:10263`).

## Equivalence: `g_tser[id]` == `id < g_ntreg && g_treg[id].ok ? g_treg[id].t.serial : 0` for every id < 2^20

I checked every writer of `g_treg[].ok`, `g_treg[].t` and `g_tser`. The whole file was searched for `->ok =` / `.ok =`, `->serial =` / `.serial =`, struct stores into `g_treg[...]`, `->t =` and `memset(g_treg`. `nvn_capture.inc` and the tests were searched too.

## Can a stale serial change what `fb_prepare` decides?

The patch adds no outcome the locked read did not already allow:
- The old code read the serial in one `g_rmu` section (`:9854`) and resolved the view in a separate one (`:9859`). A registration could already land between the two.
- The relaxed load returns either the latest store that happens-before it or a newer one. Any value it returns is one the locked read could have returned had it taken the lock before the racing writer.
- No other decision in `fb_prepare` reads registry state together with the serial in one critical section.

`tex_fast_rid` (`tex_rid_`, `:5296-5302`) does **not** re-check the serial. It resolves whatever `tid` holds now, so the brief's premise is only half true. Suppose a game thread re-registers `tid` between `:9854` and `:9859`, on either HEAD or HEAD plus the patch:
- `fb_prepare` matches the attachment by the old serial.
- It then takes the view of the new registration.
- It snapshots that texture's base under the attachment's `fb_snap` key, `(ser, lv, sl)` (`:9827`).
- In mode 1, a later draw that really samples the attachment before the next barrier could reuse that wrong snapshot.

The `g_fb_dread` decision at `:9856` has no re-check at all: a race there means one extra or one missing pass split.

This was there before the patch and is out of C3's scope. It needs the game to re-register a descriptor that a command list being replayed samples. If it is ever wanted, the fix is to compare `g_treg[tid].t.serial == ser` inside the `:9859` critical section. I make no finding against C3.

## Other checks

- **Lock order.** The patch only removes a lock acquisition, so it adds no nesting. It also takes `fb_prepare :9854` out of the one real `g_rmu`-in-`g_rmu` path in `locks.md`, the `DM_NVN_FUSE_CHECK` row of Nestings. That path runs `encode_args_` / `draw_tex` (which hold `g_rmu`) → `tex_upgrade_pfv` → `blit` → `rp_end` → `fz_end` → `fz_check_run` → `draw_` → `fb_prepare`. `fz_end` clears `g_fz.active` (`:9101`) before `fz_check_run` (`:9102`), so the inner `fb_prepare` passes its `:9842` early return. Before the patch it then aborted at `:9854` for any sampled binding. Now it only reaches `g_rmu` at `:9859`, when a sampled texture's serial equals a colour attachment's. The recursion is narrowed, not removed: `image_prepare` `:7709` and `encode_args_` `:7959` remain.
- **Scope and style.** One line, exactly the item, inside the catalog's `9852-9855`. No comment was added or removed, nothing was reformatted, and there is no debug code. `h_ser` is defined at `:8826`, before `fb_prepare` (`:9839`). The `(uint64_t)tid` cast and the second mask are harmless.
- **Semantics.** Metal and the guest receive exactly what they did before: the same serial on every path that is not a race (table above).
