## What the diff does

1. `NvArena` keeps its buffer's CPU pointer `cpu`, read once when the arena is made (`arena_new`). The buffer out-parameter of `arena_alloc` may be `NULL`.
2. The four allocations of `encode_args_` pass `NULL` and write through `g_cur_arena->cpu`: push constants, the driver segments c0 / c2, the border block and the argument block. `USE` and `g_c0_dim_buf` take `g_cur_arena->buf`.
3. `NvShader.ab_buf` becomes `__unsafe_unretained`: it is still the reuse test's non-nil flag and `t_feedback`'s view of the block. `bind_args` loses its unused `ab` and `off` parameters.

## The claim

**It holds, but the cost was not where the catalog put it.**
- `-[MTLBuffer contents]` is declared `NS_RETURNS_INNER_POINTER` (`MTLBuffer.h:46`). So ARC calls `objc_retainAutorelease` on the receiver before every `.contents` send. Every allocation in `encode_args_` autoreleased the arena buffer, despite the `__strong` out-parameter that `docs/reference/frame-rate.md` ("Arena buffer ownership on allocation") credits with avoiding that.
- On top of that, each allocation paid:
  - `objc_storeStrong` in `arena_alloc`;
  - the release of the local;
  - for the argument block, `objc_storeStrong(&sh->ab_buf)`.

**Codegen, DK host, `encode_args_` in `cand-P2` against `cand-C1`:**

| | `cand-P2` | `cand-C1` |
|---|---|---|
| `objc_retainAutorelease` | 14 | 10 |
| `objc_msgSend$contents` | 15 | 11 |
| `objc_release` | 104 | 102 |
| `sh->ab_buf` store | `bl objc_storeStrong` | `str x10, [x22, #0xd60]` |
| instructions in the function | 6,724 | 6,693 |

- Host-wide, `retainAutorelease` immediately followed by `contents` drops from 98 sites to 94.
- `arena_alloc` itself gains one `contents` send, in the inlined `arena_new`, once per new arena.

**Callers checked:**
- `arena_alloc` has 29 call sites: 24 in `nvn_mtl.m`, 3 in `nvn_geometry.inc`, 2 in `nvn_feedback.inc`.
- `bind_args` has 2 (`:7947`, `:8212`).
- `ab_buf` is read in 3 places: `nvn_mtl.m:7946` (flag only), and `t_feedback.m:66` and `:74` (the test reads the block through it, which is why the field is kept unretained rather than removed).
- `g_c0_dim_buf` was already `__unsafe_unretained`. Its only reader is the indirect dispatch copy at `:10893-10897`.

**Lifetime: the strong `ab_buf` protected nothing.**
- Arena buffers are owned by the `NvArena` objects in `g_arenas` and `g_sub_arenas`. They are released only in `arena_begin`, for arenas over `ARENA_KEEP`, after GPU completion and `ARENA_IDLE` submissions.
- A block is reused only when `ab_pass == g_pass.serial`. The serial grows monotonically (`:4211`; `:8734` restores a saved copy), so a block is reused only within its own pass, while its arena is still in `g_sub_arenas`.
- So the strong reference only kept the `MTLBuffer` object of a removed arena alive, and that block could never be bound again.
- A shared buffer's `contents` is fixed for the buffer's life. A recycled arena keeps its buffer, and so its `cpu`.

**`g_cur_arena` between each allocation and its use:**
- Each of the four sites reads `g_cur_arena` right after its own allocation.
- The c0 fill in between calls only `c0_ssbo_base`, `c0_sample_rows` and `dm_sdk_ounce`, none of which allocates.
- The old code already read `g_cur_arena->gpu` at the same points.
- `bind_args` → `enc_r_vbuf` / `enc_r_args` / `enc_c_args` do not allocate.

**Not changed (outside the item):**
- The other 25 call sites still pay `retainAutorelease` + `contents` + release per allocation. These are `ubd_shadow`, `ubp_get`, the texture-buffer rows, the unaligned vertex stream, `pull_bind`, `vconv`, `at_bind` / `lo_bind`, index expansion (`:10736`, `:10758`), the indirect expansions, copies, clears, `nvn_feedback.inc` and `nvn_geometry.inc`.
- Several of them hand the buffer object on (`:4926`, `:5450`, `:11111`, `nvn_feedback.inc:10`).
- The per-draw ones (`ubp_get`, `pull_bind`, index expansion, `nvn_geometry.inc:442` / `:652`) are a follow-up with the same pattern.

## Cost

### Microbenchmark

- The program is `scratchpad/c1/micro/micro_args.m`. The production `encode_args` runs in a loop, inside a pass or compute encoder, in 40 submissions of 500-1,000 encodes. The figure is the median of rounds 9-40, per encode.
- The thread's retired instructions come from `thread_selfcounts`, and the time is thread CPU time.
- "old" is built from a `git archive` export of `eeef8ab0` (`/Volumes/Hangar/Games/overnight/src-C1-base`) and "new" from the tree; both use the Pokopia profile. Each ran twice, alternating, under the guard.

## What did not hold

- **The catalog's cost per allocation (35-180 ns).** It is about 12-20 ns, plus one release at the pool's drain. On DK that is about 0.01-0.05 ms a frame, not 0.05-0.3 ms.
- **Where the cost was.** It was the `contents` inner-pointer `objc_retainAutorelease` and the `objc_storeStrong` calls, not only the strong out-parameter.
- **`ab_buf` is not "used only as a flag".** `t_feedback` reads the encoded block through it, so the field stays, as an unretained pointer.
- **A stale docs entry (for the main thread).** `docs/reference/frame-rate.md`, "Arena buffer ownership on allocation", says `__strong` avoids autoreleasing the arena buffer at every allocation. Every `.contents` send on a strong local still autoreleases it, and the remaining 25 call sites still do. That entry needs a correction, and possibly this item as its new Fix / Found on. Outside my files.
- **The tree's build outputs.** `dm/host/dmhost`, `dm/gfx/tests/nvn_replay` and the suite binaries are Pokopia builds of `eeef8ab0` + C1. `t_arena_args` was rebuilt last for Pokopia as well. No game was booted.
