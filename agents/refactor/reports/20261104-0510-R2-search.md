# R2 search: ASTC (and other compressed) content in DM_NVN_CAPTURE / nvn_replay

Read-only search. Nothing was edited, built or booted. Line numbers are for the working tree at `0eec4184` (branch `refactor`).

## Answer in short

Only one function decides whether a format can be read back, and it lacks ASTC: `cap_pf_block` (`dm/gfx/nvn/nvn_capture.inc:220-228`). Every later step already works from the per-subresource `row` / `img` / `bytes` that it returns, and those values are stored in the file. The replayer (`fill_tex`) re-uploads from the stored values and never computes a block size itself. So the fix is a change to `cap_pf_block` only:
- no file-format change (`CAP_VERSION` stays 1);
- no replayer change;
- no Metal path change. Compressed-format blits are documented and already used by the live layer on these same private textures.

Of all the formats the NVN layer creates, the 28 ASTC formats are the only ones `cap_pf_block` misses: LDR and sRGB, 14 block sizes each.

## 2. Formats the layer creates, and the mapping tables

Every texture the capture can read comes through these paths:
- `tex_desc`: `tex_mtl` (`nvn_mtl.m:3366-3371`), `pkg_upload_` (2379), `image_texture` (heap, the same descriptor);
- `tex_upgrade` / `sp_upgrade`, which keep `base.pixelFormat` (2036, 3092).

**NVN → Metal**: `dm/gfx/tex/nvn_fmt_mtl.c`.
- The enum of Metal values is at lines 6-17 (`ASTC_SRGB0 = 186, ASTC_LDR0 = 204` at line 15).
- The table `T[0x9D]` is at lines 28-73.
- ASTC is computed at line 78 with `astc_off` (line 74), which skips Metal's hole after 6x6.
- NVN ASTC formats are `0x79-0x86` (LDR) and `0x87-0x94` (sRGB) (`dm/gfx/nvn/include/nvn.h:518-545`). DK's texture is `0x8E` `RGBA_ASTC_8x8_SRGB`, which maps to 186 + `astc_off[7]` = 194.

**Block dimensions**: these exist only keyed by NVN format, in `dm/gfx/nvn/nvn_tex.c:12-30` `fmt_of`:
- ASTC dims are at lines 13-14 (16 bytes per block);
- BC is at lines 15-17;
- it is exported as `nvn_fmt_bpb(format, &bw, &bh)` (`nvn_tex.c:32`, `nvn_tex.h:20`).

The upload path uses this table to write every ASTC texture (`pkg_upload_` pitch `ceil(w/bw)*bpb`, `nvn_mtl.m:2433`, `2464`).

There is no table keyed by Metal format that has ASTC block dimensions. The Metal-keyed helpers give bytes only:
- `mtl_pf_bytes` (`nvn_mtl.m:2484`, plain formats);
- `bc_block_bytes` (`3912`);
- `shrt_block` (`3919`, BC + D16/D32F with the side);
- `mtl_pf_block_bytes` (`11053-11058`: BC, ASTC = 16 and EAC/ETC2 = 8/16, but no dimensions).

These Metal formats are never created by the NVN layer, so they are out of scope:
- **ASTC HDR (222-236):** NVN has no HDR ASTC.
- **EAC/ETC2 (170-183):** no NVN format maps to them.
- **PVRTC (160-167):** deprecated macOS 11-15 in the SDK header; it would also need `MTLBlitOptionRowLinearPVRTC`.
- **GBGR422 / BGRG422 (240-241).**
- **BGR10_XR / BGRA10_XR:** CAMetalLayer only.
- **Depth24Unorm_Stencil8 (255) and X24_Stencil8 (262):** NVN D24S8 maps to D32FS8.
- **NVN's 3-component formats and signed RGB10A2** (`T` entries `N`): `tex_desc` returns nil (`nvn_mtl.m:1973`), so no texture exists.
- **External textures** (serials from 2^62 up, `mtl_ext_tex` `nvn_mtl.m:12849`): GL/Vulkan swapchains, not NVN captures.

**Still not captured after the fix:** multisampled textures (`nvn_capture.inc:276`). That limit is separate and is not a format.

## 3. Does Metal allow the readback for ASTC, and does private storage need another path?

- **Yes, it is allowed.** Apple's documentation for `copyFromTexture:sourceSlice:sourceLevel:sourceOrigin:sourceSize:toBuffer:destinationOffset:destinationBytesPerRow:destinationBytesPerImage:options:` says:
  - "If `sourceTexture` uses a compressed pixel format, set `sourceSize` to a multiple of the pixel format's block size. If the block extends outside the bounds of the texture, clamp `sourceSize` to the edge of the texture";
  - "If `sourceTexture` uses a compressed pixel format, set `destinationBytesPerRow` to the number of bytes between the starts of two row blocks";
  - the offset must be a multiple of the pixel size (here, the 16-byte block).

  The only special cases it names are combined depth/stencil (the plane option, already used) and PVRTC (`rowLinearPVRTC`). The buffer→texture method used by `fill_tex` has the same rules. Source: the doc JSON of both methods on developer.apple.com.
- **Every capture value meets these rules.** `row` = blocks per row × 16. `sourceSize` = the full level, clamped at the edge (for example the 1x1 and 4x4 levels of an 8x8-block texture are one block). Offsets are sums of `bytes`, which are multiples of 16.
- **Platform support is not a concern.** ASTC formats are available from macOS 11.0, and ASTC is in Apple GPU family 2 (every Apple silicon Mac; Metal feature set tables). The layer already creates ASTC textures, and `dm/gfx/tex/tests/t_fmt_mtl` creates every mapped format on the local device (`dm/gfx/tex/README.md`).
- **Private storage does not need another path.** The capture blits into a `MTLResourceStorageModeShared` buffer and reads `contents` after `waitUntilCompleted` (`nvn_capture.inc:240-248`, `289`). `getBytes` is the one call that is not allowed on private textures (Apple: "Don't use this method for textures where storageMode is MTLStorageMode.private"), and the capture does not use it.
- **Usage flags do not matter.** The only requirement on the blit's source or destination texture is `isFramebufferOnly == false`, which every descriptor-made texture has. Copy-destination usage (ShaderRead only, `nvn_mtl.m:2020`) is irrelevant.
- **The live layer already does the same blit on ASTC.** `copy_t2b` (`nvn_mtl.m:10934-10954`, any format, `row = ceil(w/bw)*bpb`) and `mirror_readback` (`11059-11067`, ASTC accepted through `mtl_pf_block_bytes`) both copy from these private textures into buffers. The upload path writes ASTC with the same strides.
- **One small mismatch with the docs, no change needed.** The docs ask for `destinationBytesPerImage` 0 for 2D. The capture, `fill_tex`, `copy_t2b` and `mirror_readback` all pass `img` for 2D, and that already works for BC and plain formats.

**Could not establish:** that a game run has actually executed `copy_t2b` or `mirror_readback` on an ASTC texture (no log of it was looked for). Only the documentation and the upload direction are proven in use.

## 4. Smallest change, and how to pin it

### Change (one function, `nvn_capture.inc:219-228`)

Map the Metal format back to an NVN format the layer maps to it, and take that format's block from `nvn_fmt_bpb`. This uses the same tables the upload path writes the texture with, so it covers every compressed format `nvn_fmt_to_mtl` can produce by construction. Both helpers are visible in that translation unit: `nvn_fmt_mtl.h` through `nvn_mtl.m:22`, `nvn_tex.h` through `nvn_capture.h` → `nvn_obj.h:8`, and `fmt_compressed` at `nvn_mtl.m:1714`. Before the final `*bw = *bh = 1; return 0;`:

```c
for (int nf = 1; nf <= 0x9C; nf++) { uint32_t m; int w, h; if (fmt_compressed(nf) && nvn_fmt_to_mtl(nf, &m, NULL) && m == (uint32_t)f) { b = nvn_fmt_bpb(nf, &w, &h); *bw = (uint32_t)w; *bh = (uint32_t)h; return b; } }
```

The BC lines can stay (no diff), and the loop then only ever matches ASTC.

An equivalent alternative is a Metal-keyed ASTC table:
- `k = (f - MTLPixelFormatASTC_4x4_sRGB) % 18` for 186 ≤ f ≤ 236;
- k ≤ 14 and k ≠ 5 (Metal's hole after 6x6, and the gaps 201-203 / 219-221);
- dims `{4,4},{5,4},{5,5},{6,5},{6,6},-,{8,5},{8,6},{8,8},{10,5},{10,6},{10,8},{10,10},{12,10},{12,12}`;
- 16 bytes per block.

It also covers HDR, but it repeats numbers that `nvn_fmt_mtl.c` / `nvn_tex.c` already hold.

The rest of the change:
- Correct the comment at `nvn_capture.inc:219`, which the change makes wrong.
- Correct `docs/development.md:515`: "multisampled textures and formats that are not plain texels are not captured" becomes multisampled only. BC was already captured, so this line was stale before.
- Optionally add a `docs/reference/nvn-objects.md` entry (Symptom: the `format 194 … content not captured` red line and magenta / noisy replays; Found on: DK Bananza), then run `python3 dm/tools/docs_symptoms.py`.
- Recapture the existing DK captures: they lack the TPIX. Old files still load, because the format is unchanged.

### Test (`dm/gfx/tests/t_capture_live.m`, run by `make -C dm/gfx/tests GAME=<id> check_t_capture_live`, Makefile:142-146)

`t_capture.c` is CPU-only and links only `nvn_capture.c` (Makefile:136-137). It cannot reach `cap_pf_block`, which uses `MTLPixelFormat`. `t_capture_live.m` includes `nvn_mtl.m`, and through it `nvn_capture.inc`, and links `../tex/*.c` and `nvn_tex.c` (`GFX`, Makefile:15, 28). It needs two additions.

1. **Table pin (static, cheap).** For every `nf` in 1..0x9C with `nvn_fmt_to_mtl(nf, &pf, NULL) && pf`:
   - `cap_pf_block((MTLPixelFormat)pf, 0, &bw, &bh)` must be non-zero;
   - for non-depth formats (`!fmt_depth(nf)`, `nvn_mtl.m:1715`; D32FS8 is 4+1 in Metal, 8 in NVN) it must equal `nvn_fmt_bpb(nf, …)` with the same `bw` / `bh`.

   Today this fails for the 28 ASTC formats.
2. **End to end (a DK-shaped copy destination).**
   - Frame 1: a `tex_t at`, 2D, `NVN_FORMAT_RGBA_ASTC_8x8_SRGB` (0x8E), 16x16, 3 levels (2x2 blocks, then 1 block, then a 4x4 level clamped to its edge). It gets `nvn_tex_layout` and `mtl_tex_init`, with no pool and no storage like `rt`. An `OP_COPY_B2T` of 64 non-zero bytes from the pool fills level 0.
   - Frame 2, first submit: `OP_COPY_T2B` of `at` level 0 (16x16) to `pool + 0x38000`, then in the same submission `OP_COPY_B2T` from there into `rt` at (48,48), 4x4 RGBA8 (64 bytes, clear of the other copies). Consecutive blits get a barrier (`blit()`, `nvn_mtl.m:1099-1103`).
   - Both copies must be in one submission. Across submits, the capture's PDIF would carry the live T2B result and hide the missing texture.
   - The presented digest then depends on `at`'s content at the frame's start, which only its TPIX carries. Without the fix the replay's `at` is undefined, and `nvn_replay --repeat 2` reports MISMATCH (exit 1).
   - Add `if (g_cap_tex_skip) FAIL` beside the checks at `t_capture_live.m:81-82`, so a texture left out is reported at capture time.

   Afterwards, `check_t_capture_live` also exercises `fill_tex` on ASTC: the pixel format, level and slice equality, and a compressed `copyFromBuffer` with the clamped edge level.
