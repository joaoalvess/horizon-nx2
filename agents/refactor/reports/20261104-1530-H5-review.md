# H5 review: `dm_yield_to_core_peers` waits on a condition variable

Reviewer, item mode. Diff: `git diff -- dm/host/hle_thread.c dm/host/tests/Makefile` plus the untracked `dm/host/tests/t_handoff_wake.c`, on `refactor` (code as at `32913850`). Line numbers are in the working tree. Read-only: nothing was built or run.

**Verdict: approve with nits**

No correctness defect found. Every writer that can end the wait and runs under `G` wakes the waiter, the scan and the wait share one hold of `G`, and the H3 invariant holds. The nits are a wasted broadcast in all-peers mode, docs this change makes wrong, and test details.

## Predicate writers

The wait is `hle_thread.c:213-215`. It is under `G` from the scan to `pthread_cond_timedwait_relative_np`, which releases `G` atomically. `hand_wait` and `g_hand_waiters` are set in the same hold. So a writer under `G` either runs before the scan, which sees it, or after the waiter is queued on `g_hand_cv`, where its broadcast reaches it. No wake-up is lost between the scan and the wait.

No `G` writer is missed. Spurious wake-ups only rescan. The re-check never gets longer than 50 µs: each wake rescans before it waits again.

Paused or suspended waiter: the waiter is inside the SVC (`hle.c:128`), so a pause on it counts at once, as on HEAD. `hand_wake` on it is a harmless extra broadcast. It parks in `thr_svc_leave` after the wait.

## H3 and lock order

- **H3 invariant.** The wait runs after `svc_thread`'s `cv_flush` (`:957` before `:963`), and its hold queues no signal. So the new implicit release of `G` has nothing to flush, and no `G` is taken between an unlock and its `cv_flush`.
- **No deadlock with `thr_free`.** When `thread_exit` broadcasts and then spins in `thr_free` holding `G`, the woken waiter only waits for `G`. It owes no `cv_flush`.
- **Signalled under `G`, not through the deferred list.** This is safe: `g_hand_cv` is global, never destroyed and outside the `cv_pend` protocol.
  - In the default mode a hit is about one per handoff (MKW about 13 a second).
  - That hit comes almost always from `block`, which H3 already lets signal under `G`.
- **Hot-path cost in the default mode.** Each wake and each block adds one load of `g_hand_waiters`. While a handoff is in progress, it also adds a loop of at most 4 entries.
- **Lock order.** No new order. `g_hand_cv` is used only with `G`. `g_sub_mu`, `pcv` and `dm_host_lock` paths are unchanged.

## Findings

1. **Nit, performance: all-peers mode broadcasts on every state change.** At `hle_thread.c:147` the test is `hit = g_core_preempt || ...`. So under `DM_PREEMPT=1` or `core_preempt` (no profile of the fork's games sets it), every `note_runnable`, `hand_leave`, exit, priority change and pause of any thread broadcasts while anyone waits.
   - This covers threads on other cores, lower-priority threads and host-owned threads.
   - It also includes `note_runnable` (`:262`). Making a thread runnable can never end an all-peers wait, because `nhand` is not consulted when `all` is set.
   - Each broadcast is a psynch syscall under `G`. That is the per-waking-SVC cost H3 removed (0.4-1.8 µs). Every waiter then wakes and rescans `g_all` under `G`.
   - Scenario: with `DM_PREEMPT=1`, a pinned thread waits while workers on cores 1 and 2 ping-pong on a condition variable. Every one of their SVCs pays a broadcast under `G` and causes a full rescan.
   - Fix: skip `hand_wake` in `note_runnable` when `g_core_preempt` is set, and in all-peers mode require the target to be pinned and not `host_owned`.
2. **Nit, docs this change makes wrong** (`CLAUDE.md`: correct them, then run `docs_symptoms.py`):
   - `docs/reference/threads.md:77`: "`dm_yield_to_core_peers` → `nanosleep`". A sample now shows `pthread_cond_timedwait_relative_np`.
   - `docs/reference/threads.md:235`: "before its starter's 50 µs poll sees it". The starter is now woken by the leave itself.
   - `agents/architecture/host-threads.md` "Same-core handoffs" 3.3 ("sleeps 50 µs and scans again"). The Global state and `thr_t` tables lack `g_hand_cv`, `g_hand_waiters` and `hand_wait`.
   - `agents/architecture/locks.md` row `G`: a new condition variable, signalled under `G`, and a new wait site.
3. **Nit, test.**
   - `t_handoff_wake.c:108` prints `FAIL:` without the `[RED] ` prefix that `t_cvsignal` and `CLAUDE.md` use.
   - The exact counts `n == 2` (`:168`) and `n == 1` (`:184`, `:220`) fail on a single spurious return of `pthread_cond_wait`. That is rare on Darwin. Counting broadcasts would be more robust.
   - The test reads `hand_wait`, so it does not build on HEAD. It cannot show HEAD's behaviour, only mutants of the new code.
   - What it does well: untimed waits for `S` turn a lost wake-up into the 20 s alarm. It covers each of the six `hand_wake` sites, the wait being in one hold with the scan (`scan_window`), the bound (`host_work_recheck`), the filter (`unrelated`) and two waiters on one condition variable (`stress`).
   - The Makefile target matches `cvsignal` and `preempt`, and running it from `run` is right.
4. **Observation, not a defect: in all-peers mode a sleeping peer is seen only at the re-check.**
   - SleepThread with `nhand == 0` (`:1007`) never broadcasts.
   - When it has `nhand`, its broadcast comes before `sleeping` is set without `G` (`:951`). The waiter rescans, still sees the peer as runnable, and waits again.
   - Latency is the same as HEAD. The test skips these cases in `--all-peers` for this reason.
   - `host_owned` (`:134`) is likewise bound-only. A spawner holding for a host thread waits up to 50 µs, as before.
5. **Observation: `dm_thread_service_request` still polls.** Its own 50 µs `nanosleep` poll (`:174-179`) lies inside the catalog's range (160-205) and is unchanged. Its wake source, `hand_epoch++` (`:966`), is written without `G`. The main thread should decide whether H5 covers it.
