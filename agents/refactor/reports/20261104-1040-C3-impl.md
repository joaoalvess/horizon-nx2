# C3 impl: `fb_prepare` reads a binding's serial without `g_rmu`

## Files changed

- `dm/gfx/nvn/nvn_mtl.m`: 1 line (`:9854`).

```
-        os_unfair_lock_lock(&g_rmu); uint64_t ser = tid < g_ntreg && g_treg[tid].ok ? g_treg[tid].t.serial : 0; os_unfair_lock_unlock(&g_rmu);
+        uint64_t ser = h_ser((uint64_t)tid);
```

The patch is `/private/tmp/claude-501/-Users-joaoalves-Developer-switch/fd5fcbce-ad70-4407-952b-560d6e7b6b20/scratchpad/c3/C3.patch`; `git apply --check -R` passes. The working diff of `nvn_mtl.m` is now this hunk alone.

## What the diff does

1. `fb_prepare`'s binding loop took `g_rmu` for every fragment TEX binding with a texture ID. It needed the lock only to read the ID's serial and compare it with the attachments.
2. The loop now reads the serial from `g_tser`, through the existing `h_ser` (`:8826`). `g_tser` is the lock-free ID → serial copy that `mtl_reg_tex` publishes under `g_rmu` (`:4810-4812`, `:5023`). The store lookahead and the clear hoist already read it the same way.
3. `g_rmu` is still taken at `:9859` (`tex_fast_rid`), but only for a binding whose serial is a colour attachment of the pass.

## The claim

**It holds.** Every fragment TEX binding with a non-zero ID took and released `g_rmu` at `:9854`. That is 2,900-4,100 times a frame on the heavy captures (counts under Cost).

**`g_tser` gives the same answer as the locked read.** For every ID below 2^20, `g_tser[id] == (g_treg[id].ok ? g_treg[id].t.serial : 0)` whenever `mtl_reg_tex`'s critical section is not running:
- Only `mtl_reg_tex` writes `ok` and `t` (`:5015`), and the same branch stores `g_tser[id] = t ? t->serial : 0` (`:5023`). Its "same" path changes neither.
- Growth (`:5006`) zero-fills new entries, and `g_tser` is zero-initialised BSS. An ID at or past `g_ntreg` was never registered, so both reads give 0.
- `treg_gone` (from `mtl_reg_tex_gone` and `treg_drop_pool_views`) sets `gone` and drops views. It keeps `ok` and the serial, and leaves `g_tser` alone, so both reads still give the serial.
- `tid` comes masked to 20 bits (`& 0xfffff`), so it always indexes inside `g_tser`.
- Nothing else writes registry entries. `rg` over `dm/gfx` finds only `mtl_reg_tex`. The replayer restores registries through `mtl_reg_tex` (`nvn_replay.m:338`). The one test that fills `g_treg` itself (`t_tex_fit_root`) never reaches `fb_prepare`.

**Nothing depended on the lock's ordering.**
- The serial is compared only with `R.rt`, which is submit-thread state.
- The view is then resolved under `g_rmu` at `:9859`, where `tex_rid_` and `tex_by_id` check `tid < g_ntreg && ok` again.
- A registration racing the draw could already land between the old `:9854` and `:9859` locks, so the relaxed read adds no new interleaving.

**The loop body cannot change what a later binding reads.**
- `tex_upgrade_pfv` and `tex_upgrade` take a `const tex_t *`. They replace the Metal texture and bump `g_ser_gen`, but leave the registration's serial alone.
- `rp_end` runs here with `g_fz.active` clear (`:9842`), so it redoes no draws.

**Locks.** Nothing is added to the nesting graph in `agents/architecture/locks.md`: `:9854` held `g_rmu` only around plain reads and made no calls. Its `g_rmu` row lists `fb_prepare` at `:9854` and `:9859`. After C3 only `:9859` remains; that file belongs to the main thread.

**Codegen.** In the DK host, `fb_prepare` is inlined into `draw_`. Comparing `cand-C1` with `cand-C3`:

| In `draw_` | `cand-C1` | `cand-C3` |
|---|---|---|
| `bl _os_unfair_lock_lock` | 2 | 1 |
| `bl _os_unfair_lock_unlock` | 3 | 1 |
| lines | 9,984 | 9,968 |

- In `cand-C3` the lookup is a single `ldr` from `_g_tser`.
- The remaining lock and unlock are the ones at `:9859`.

**Callers.**
- `fb_prepare` has one production call site, `draw_` at `:10512`.
- Only `t_feedback` calls it directly (12 call sites).
- `h_ser` itself is unchanged. It has 12 other call sites, among them the same per-binding serial lookups in `fz_p2_draw` (`:9593`), `:9458` and `:10263`.

## Cost

### Microbenchmark

- **The program.** `scratchpad/c3/micro/micro_fb.m` calls the production `fb_prepare` 1,000 times a round, for 40 rounds. The draw has a colour attachment and fragment TEX bindings whose textures are registered but are not attachments. The figure is the median of rounds 9-40, per call, from `thread_selfcounts` instructions and thread CPU time.
- **The builds.** "old" is built from an export of `HEAD` + `C1.patch` (`/Volumes/Hangar/Games/overnight/src-C3-base`, equal to the tree except the C3 line). "new" is built from the tree. Both use the DK profile. Each ran twice, alternating, under the guard.

| Case | old | new | Saved |
|---|---|---|---|
| no TEX binding | 167.3 instr, 9.5-12.4 ns | 163.3 instr, 9.5-12.0 ns | 4 instr |
| 1 TEX binding | 238.3 instr, 14.1-17.4 ns | 208.3 instr, 11.8-15.1 ns | 30 instr, about 2.5 ns |
| 8 TEX bindings | 805.3 instr, 44.7-64.2 ns | 586.3 instr, 30.9-40.6 ns | 219 instr (27 a binding), 14-24 ns |
| 8 TEX bindings, another thread calling `mtl_reg_tex` on another ID in a loop | 1,049-1,774 instr, 396-517 ns (runs up to 2.6 µs) | 586.3 instr, 31-41 ns | 0.36-0.48 µs a call, about 45-60 ns a binding |

- **The ns ranges** come from two clock states that alternated between runs. Within each run every row is tight.
- **Uncontended**, each binding saves the lock and the unlock: about 27-30 instructions and 2-3 ns.
- **The contended row** is a synthetic worst case. It shows what a game thread registering textures during submission costs each binding the submitter checks; the new code no longer waits there at all.

## What did not hold

- **The catalog's cost.** Uncontended, it is about 2-3 ns a binding, 7-12 µs a frame, not 0.1-0.3 ms. The rest of the item's value is the removed exposure to registration contention, which replays cannot measure.
- **How the fix works.** It is not "lock once per draw". The existing lock-free copy `g_tser` made the lock unnecessary for this read, so the loop now takes no lock unless a binding is an attachment.
- **Stale docs (for the main thread).** `agents/architecture/locks.md`, the `g_rmu` row: its holder list has `fb_prepare` `:9854`, which C3 removes.
- **The tree's build outputs.** `dm/host/dmhost`, `dm/gfx/tests/nvn_replay` and the suite binaries are Pokopia builds of `b2cb3e7d` + C3. No game was booted.
